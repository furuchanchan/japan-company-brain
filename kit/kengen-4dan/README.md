# 権限のひな形（4段）

gbrain に、日本の会社でよくある4段の権限（役員・部門・全社・社外）を1回で入れる道具です。
本家 gbrain のコマンドを順に呼ぶだけで、本家のコードは変えません。確かめた版は v0.60.736.0（2026-11-18）です。

入っている物は2つです。

- `apply.ts`：会社の形（company.json）を読み、置き場・メンバー・グループ・フォルダの決まり・鍵を入れる
- `check.ts`：1人ずつの鍵で実際に呼び出し、読める・読めないが決めた形どおりかを表にする
- 会社の形の見本は、リポジトリの `config/company.example.json` にあります

## 4段でできること

| 段 | 読める物 | 書く先 |
|---|---|---|
| 役員（yakuin） | 全社と全部門。全社の役員フォルダ（例 `keiei/`）も読める | 全社 |
| 部門（bumon） | 自分の部門と全社。ほかの部門と役員フォルダは読めない | 自分の部門 |
| 社外（shagai） | 全社のうち、名指ししたフォルダ（例 `shagai/`）だけ | 書けない |

全社は、役員と社員の全員が読む置き場です。部門は、部門ごとに置き場を1つ作ります。
この4段で足りない所は、`rules` に追加の決まりを書きます（例：人事の `hyoka/` は人事と持ち主だけ）。

## ひな形が要る理由

本家は、安全な側に倒れる既定で作られています。そのまま入れると、次の2つで止まります。どちらも手元の検証で確かめました。

1. メンバーの鍵で AI が書いた新しいページは、読み手が書いた本人だけになります。同じ部門の人にも、社長の鍵にも出ません。フォルダの決まりは読み手を絞る向きにしか働かないので、決まりを足しても広がりません。
   置き場を「連合しない」設定（`--no-federated`）で作ると、この印が付かず、その置き場を読める鍵（同じ部門と役員）がそのまま読めます。このひな形は、全社と部門の置き場をすべてこの設定で作ります。
2. 人に結ばない鍵は、2人以上の記憶では作れません。このひな形は、先にメンバーを登録し、鍵を1人に1つ、必ずメンバーに結んで作ります。

## 入れ方

この一式では `./brain apply`・`./brain sync`・`./brain check` が、下のコマンドを代わりに呼びます。道具だけを別の gbrain に使う時は、gbrain を動かしているホストで下のとおり実行します（Bun が要ります）。

1. `config/company.example.json` を写して、会社の形を書く
   - `owner`：持ち主（役員から1人）。すべての決まりの読み手に必ず入ります
   - `zensha`：全社の置き場。`path` は文書のフォルダ、`yakuin_folders` は役員だけのフォルダ、`shagai_folders` は社外にも出すフォルダ
   - `departments`：部門ごとの置き場
   - `members`：1人ずつ。`dan` は `yakuin`・`bumon`・`shagai` のどれか。`bumon` には `department` を書く
   - 文書のフォルダが git の管理でない時は、置き場に `"plain_directory": true` を書く（見本はこの形）
   - `rules`：追加の決まり。`{"source": "jinji", "prefix": "hyoka/", "readers": ["group:jinji"]}` の形
2. 下見をする（何も変えません。実行するコマンドが順に出ます）

   ```bash
   bun apply.ts company.json
   ```

3. 入れる（鍵は、指定したフォルダに1人1ファイル、本人だけが読める権限で置きます。画面には出しません）

   ```bash
   bun apply.ts company.json --keys ./member-keys --yes
   ```

4. 文書を取り込む

   ```bash
   gbrain sync --all
   ```

5. 確かめる（窓口を `gbrain serve --http` で動かしてから）

   ```bash
   bun check.ts company.json --keys ./member-keys --url http://127.0.0.1:3131 --write-test
   ```

   `--write-test` を付けると、部門ごとに1人が確かめ用のページを1つ書き、同じ部門と役員が読めて、ほかが読めないことまで見ます。ページは終わりに消します。付けなければ読むだけです。
   決めた形と違う所が1つでもあれば、表に ★ が付き、終了コードが1になります。

入れ直しても、既にある置き場・メンバー・グループ・決まり・鍵は飛ばします。人を足す時は、`members` に足して同じコマンドをもう1度実行します。

## 後からの変更

- 退職・異動：`gbrain access member disable <id>`。その人の鍵は、次の呼び出しから使えません（鍵の作り直しは要りません）
- 既にある鍵を人に結び直す：`gbrain auth rescope --token <鍵の名前> --member <id>`
- 決まりを広げる変更は、本家が承認を待ちます。下見で、だれが読めるようになるかが出ます

## AI から書けない時

新しく立てた記憶では、AI が書いたページはファイルにも残り、何もしなくて書けます。
`owner_unavailable` で断られるのは、記憶が古い形（classic）の時です。古い版から上げた記憶や、書き手の設定を外した記憶がこれに当たります。本家の考えは、ファイルを書けるホストを1台に決めるまでは、AI にファイルを書かせない、というものです。

`company.json` の `kakikomi` で、直し方を選びます。3つとも、古い形の記憶で確かめました。

| kakikomi | すること | 結果 |
|---|---|---|
| `sonomama`（既定） | 何も変えない | 古い形の記憶では、AI からの書き込みは断られる。人がファイルを直して `gbrain sync` で取り込む |
| `database` | 書き手の決まっていない置き場には、DB にだけ書く | 書ける。ファイルには残らない（ファイルのバックアップや git の履歴に入らない） |
| `file` | このホストを各置き場のファイルの書き手に決め、managed を有効にする | 書ける。ファイルにも残る |

`file` は、ファイルの書き手を1台に決める設定です。記憶を2台以上のホストで動かしている時は、先に本家の `docs/architecture/topologies.md` を読んで、どのホストを書き手にするかを決めてください。

## 確かめた範囲と、まだの所

- 確かめた：見本の会社（役員2人・営業2人・人事1人・社外1人、置き場3つ、文書9件）で、読む側36か所と書く側13か所の計49か所が、決めた形どおり。入れ直しで足される物は0件
- まだ：2台以上のホストで動かす構成、git で管理した文書の置き場（書いたページが commit されるか）、100人をこえる会社での入れる時間

## 注意

- 鍵のファイルは秘密です。配る時は、1人ずつ安全な経路で渡し、渡した後はホストから消してください
- 記憶を1台のホストに2つ立てる時は、内容の置き場の親のフォルダを分けてください。同じ親に置くと、本家が置く持ち主の目印が重なり、後から立てた記憶が古い形になります（手元で1度起きました）
- gbrain の版を上げたら、確かめ（check.ts）を回し直してください
