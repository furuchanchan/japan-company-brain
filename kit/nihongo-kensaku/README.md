# 日本語検索の直し

gbrain の言葉検索を、日本語でも使える速さと当たり方にする2つの直しです。
どちらも本家 gbrain のコードと表の形を変えずに足せます。確かめた版は v0.60.736.0（2026-11-18）です。

入っている物は4つです。

- `chukei.ts`：日本語の質問文を、語に分けてから検索に渡す中継
- `wakeru.ts`：語に分ける処理（中継が使う。試験は `bun test`）
- `ja-index.sh`：日本語の言葉検索を速くする索引を、DB で使える部品に合わせて選んで足す手順
- この手引き

## 直す前に起きること

手元の検証（架空の文書 100,000ページ、言葉検索の `search`）で確かめた事実です。

1. 質問文をそのまま投げると、0件になります。「値引きの承認は誰がしますか」など4つの質問が、4つとも0件でした。本家の言葉検索は、問いを空白で区切って語にするので、空白の無い日本語の文は丸ごと1語として扱われます。
2. 日本語の語は、毎回すべてのページを読んで探します。3ページにしか無い語「瑕疵担保」が69ミリ秒、同じく3ページにしか無い英語の語「warranty」は6ミリ秒でした。ページが増えるほど差は開きます。

## 直し1：質問文を語に分ける中継

gbrain の窓口（`gbrain serve --http`）の手前に置きます。AI のつなぎ先を、この中継の URL に変えるだけです。

```bash
bun chukei.ts --upstream http://127.0.0.1:3131 --listen 3133
```

- 直すのは、検索の道具 `search` に来た、文として書かれた日本語の問いだけです。空白で区切った語の並び・英語・1語の問いと、検索でない呼び出しは、そのまま通します
- 語に分ける時に落とす語は3つです。ひらがなだけの語（助詞・語尾）、1文字の語、述語として使われた語（「確認しました」の確認）
- 追加の部品は要りません（Bun に入っている語の区切りの機能を使います）
- 問いの中身は記録しません。語に分けて渡した呼び出しには、返事に `x-nihongo-kensaku: waketa` の印が付きます

確かめた結果（同じ4つの質問、100,000ページ）：

| 質問文 | そのまま | 中継ごし |
|---|---|---|
| 値引きの承認は誰がしますか | 0件 | 11件。上位はすべて正解 |
| 見積の確認は誰がしますか | 0件 | 10件。上位はすべて正解 |
| 熱交換器の型番はどこに確認しましたか | 0件 | 11件。上位はすべて正解 |
| 瑕疵担保の条項は誰が確認しましたか | 0件 | 3件。3ページとも正解 |

中継ごしの結果は、語に分けた問いを本家へ直接投げた結果と、件数も並びも同じでした。

述語を落とす理由も測りました。「瑕疵担保の条項は誰が確認しましたか」から「確認」を落とさずに投げると、どのページにもある語で絞り込めず、2秒の打ち切りに当たって約2.1秒かかり、正解は3ページなのに11件が返ります。落とすと、索引つきで9ミリ秒、返るのは正解の3件だけでした。

置く時の注意：

- 中継は、gbrain と同じホストで動かしてください。本家は、同じホストの中継が付けた `X-Forwarded-For` から元の相手を見分けます（回数の制限が相手ごとに効きます）
- 外から届く URL は、今までどおり本家の `--public-url` に設定します。その URL の届け先を、本家の窓口からこの中継に変えてください
- `--tools search,query` で、意味の検索を合わせる道具 `query` にも効かせられます。ただし `query` への影響はまだ測っていません。既定は `search` だけです

## 直し2：索引を選んで足す

```bash
DATABASE_URL=... sh ja-index.sh          # 下見。実行する SQL が出るだけ
DATABASE_URL=... sh ja-index.sh --yes    # 足す
DATABASE_URL=... sh ja-index.sh --remove --yes   # 外す
```

DB で使える部品を見て、pg_bigm、無ければ PGroonga、無ければ pg_trgm の順に1つ選びます。作っている間も、読み書きは止まりません。`JA_INDEX=pg_trgm` のように決め打ちもできます。

速さ（100,000ページ、言葉検索の時間。4巡の真ん中の値）：

| 語 | 索引なし | pg_trgm | pg_bigm | PGroonga |
|---|---|---|---|---|
| 瑕疵担保（4文字、3ページ） | 69ミリ秒 | 5 | 5 | 6 |
| 条項（2文字、3ページ） | 76ミリ秒 | 77 | 5 | 6 |
| 承認（2文字、よく出る語） | 91ミリ秒 | 91 | 26 | 45 |

pg_trgm は3文字ずつの索引なので、2文字の語には効きません。日本語は2文字の語が多いので、pg_bigm か PGroonga が使える所では、そちらを選びます。

索引の大きさと作る時間（100,000ページ、表は157MB）：pg_trgm 62MB・5秒、pg_bigm 51MB・6秒、PGroonga 162MB・5秒。

クラウドごとの使える部品（各社の公式の一覧で確かめた分。2026-11-18）：

| 置き場所 | pg_trgm | pg_bigm | PGroonga | 選ばれる部品 |
|---|---|---|---|---|
| Amazon RDS・Aurora | 使える | 使える | 使えない | pg_bigm |
| Google Cloud SQL | 使える | 使える | 使えない | pg_bigm |
| Azure Database for PostgreSQL | 使える | 使えない | 使えない | pg_trgm |
| Supabase | 使える | 使えない | 使える | PGroonga |
| 自分で立てた Postgres | 使える | 入れれば使える | 入れれば使える | 入れた物 |

採らなかった案：PGroonga 独自の検索の書き方（`&@~`）。速さは出ますが、本家の SQL を書き換えることになり、本家の版が上がるたびに直しが要るためです。

## 確かめた範囲と、まだの所

- 確かめた：質問文4問が中継ごしに当たること、直さない呼び出しがそのまま通ること、索引の手順が3種類とも作れて、入れ直しと取り外しができること
- まだ：お客さんの実際の文書と質問での当たり方、意味の検索を合わせる道具 `query` への影響、100万ページをこえる量、クラウドの実物の上での索引づくり（手元の Docker の Postgres 17 で確かめました）

## 見直す線

本家にも、日本語の語の区切りを入れる提案があります（Discussions #8223、2026-11-18 の時点で未実装）。本家に入ったら、この中継は外して本家に合わせます。索引は、そのまま使えます。
